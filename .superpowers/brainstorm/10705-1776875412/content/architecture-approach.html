Architecture approach — how we structure the code

Same feature set, three different ways to structure it. This choice decides testability, install path, and long-term evolution.

A

Evolve the Flask monolith

Stack: Flask + Jinja + vanilla JS + Chart.js (what you have). Reorganize app.py into modules (core/, aws/, audit/, exporters/, web/) but keep the single-process web app.

Fastest to ship — familiar stack, no rewrites. Weakness: no CLI, so CI/scheduled-report users can't use it without a browser. Harder to test business logic in isolation.

B

Core library + CLI + Web UI (three surfaces, one engine) RECOMMENDED

Stack: Python core package (pure, no framework) → exposes data-fetch/audit/export as importable functions. CLI built on top with Rich (Typer). Web UI built on top with FastAPI + Jinja/HTMX (lean SPA feel, minimal JS). Same distribution as Grafana, Sentry, etc.

Users get all three: pip install → use as a library, run the CLI, or launch the web UI. Business logic is trivial to unit-test (no Flask context needed). This is the shape people expect from a self-hosted FinOps tool.

C

Full SPA rewrite (FastAPI + React/Next.js)

Stack: FastAPI backend, React or Next.js frontend with TanStack Query + Recharts/visx. Best possible UX polish. Separate npm run build pipeline.

Heaviest rewrite — 2-3× the work of (B). No CLI. Adds a Node build step to a Python package, complicating distribution (pipx install still works but bundle is larger). Worth it only if design polish is the #1 differentiator.

My recommendation: (B). Three-surface layering is the single architectural decision that lets this product grow into a real platform without repainting. Core library → CLI → Web UI. The web UI stays polished without React overhead thanks to HTMX+Alpine; if we ever want React later we swap just the frontend layer, the core stays untouched. It also makes the "accuracy invariant" enforceable — business logic sits in one testable package, not scattered across Flask routes.
